# Настройка входа: Google и письма

Приложение работает и без всякой настройки: гость играет по cookie, регистрация
по почте и паролю работает сразу. Настройка нужна для двух вещей:

- **вход через Google** — кнопка «Продолжить с Google» появляется, только если
  заданы `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`;
- **письма** — подтверждение почты и сброс пароля.

Без ключей писем ссылки не уходят наружу: они пишутся в консоль воркера, а на
`localhost` ещё и возвращаются в ответе, чтобы локально можно было пройти весь
сценарий. На чужом адресе ссылка в ответе не показывается никогда.

Секреты лежат в `.dev.vars` в корне проекта — в Git файл не попадает, пример
рядом: `.dev.vars.example`. Его читают оба режима: и `npm run dev`, и `npm start`
(так работает LAN-сервер), — проверено. На LAN-сервере положите файл в корень
проекта и перезапустите сервис: `npm ci` и сборка его не трогают. У
задеплоенного через `wrangler deploy` воркера те же имена задаются командой
`npx wrangler secret put ИМЯ`.

Письма и вход через Google независимы. Чтобы включить **только письма** —
раздел 2 и ключи `GMAIL_*`; кнопка «Продолжить с Google» при этом не появится.
Общий OAuth-клиент из раздела 1 всё равно нужен: им выдаётся токен отправки.

## 1. OAuth-клиент Google

Клиент создаётся один раз. Его ключи можно использовать и для входа
(`GOOGLE_*`), и для писем (`GMAIL_*`), и только для писем.

1. [Google Cloud Console](https://console.cloud.google.com/) → создайте проект
   (или выберите существующий).
2. **Экран согласия** → <https://console.cloud.google.com/auth/audience>
   (в обновлённой консоли «Google Auth Platform → Audience», в старой —
   «APIs & Services → OAuth consent screen»): тип «External», название
   приложения и свой адрес для связи.

   В разделе **«Test users»** добавьте адрес ящика-отправителя. Это список
   аккаунтов, которым разрешено выдавать согласие приложению, пока оно в статусе
   «Testing»; остальные получат «Access blocked». Участники, регистрирующиеся в
   Jinaly по почте, с Google не взаимодействуют — их сюда добавлять не нужно.

   Если ящик на Google Workspace, выберите тип «Internal» — тогда ни test users,
   ни публикация не нужны.
3. **APIs & Services → Credentials → Create credentials → OAuth client ID**,
   тип **Web application**.
4. В «Authorized redirect URIs» добавьте `http://localhost:3000/api/auth/google/callback`.
   Если нужен ещё и вход через Google на опубликованном домене — добавьте
   `https://<домен>/api/auth/google/callback`. Адрес должен совпадать
   посимвольно, включая схему, порт и путь.

   Для одних только писем хватает адреса с `localhost`, и **адрес сервера сюда
   добавлять не нужно**. Адрес возврата — это куда браузер возвращается с экрана
   согласия, а для писем этот экран показывается один раз, на той машине, где вы
   запускаете скрипт из раздела 2. Дальше воркер ходит за токеном отправки сам
   (`grant_type=refresh_token`), и `redirect_uri` в этом запросе нет. Токен не
   привязан к машине: получите его у себя и скопируйте строки на сервер.

   **Google принимает только `https`; исключение — `http://localhost` и
   `http://127.0.0.1`.** Адрес вида `http://192.168.1.10:3001` зарегистрировать
   нельзя, поэтому на LAN-сервере вход через Google не заработает без HTTPS:
   нужен домен с сертификатом, туннель (например `cloudflared`) или обычная
   публикация. Регистрация по почте на LAN-сервере при этом работает как обычно.
5. Скопируйте Client ID и Client secret. Куда их вписать, зависит от того, что
   включаете:

   ```
   # только письма — кнопка входа через Google не появится
   GMAIL_CLIENT_ID=...apps.googleusercontent.com
   GMAIL_CLIENT_SECRET=...

   # ещё и вход через Google
   GOOGLE_CLIENT_ID=...apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=...
   ```

   Если задан только блок `GOOGLE_*`, письма возьмут эти же ключи.

По умолчанию адрес возврата собирается из origin запроса. Если сервер стоит за
прокси и видит другой адрес, задайте `APP_URL` (и при необходимости
`GOOGLE_REDIRECT_URI`) явно.

## 2. Письма через Gmail API

В Cloudflare Workers нет SMTP, поэтому письма уходят запросом к Gmail API от
имени обычного ящика Gmail или Google Workspace. Лимит — около 500 писем в
сутки на бесплатном Gmail и 2000 на Workspace.

1. В том же проекте: **APIs & Services → Library → Gmail API → Enable**.
2. На экране согласия добавьте scope `https://www.googleapis.com/auth/gmail.send`.
3. Получите refresh-токен ящика-отправителя — это делается один раз. Остановите
   dev-сервер (скрипт займёт порт 3000) и запустите:

   ```sh
   npm run auth:gmail-token
   ```

   Скрипт спросит Client ID и секрет (или возьмёт их из переменных окружения),
   покажет ссылку согласия, дождётся возврата на `http://localhost:3000/…` и
   напечатает готовые строки для `.dev.vars`. Ключи остаются на вашем
   компьютере: запрос уходит только на `oauth2.googleapis.com`.

   Войти нужно тем ящиком, от имени которого пойдут письма. Флаг `--write`
   допишет строки в `.dev.vars` сам, `--port` меняет порт (тогда добавьте
   соответствующий адрес возврата в Console).

4. В `.dev.vars` должно получиться:

   ```
   GMAIL_CLIENT_ID=...apps.googleusercontent.com
   GMAIL_CLIENT_SECRET=...
   GMAIL_REFRESH_TOKEN=1//0g...
   GMAIL_SENDER=Jinaly <you@gmail.com>
   ```

   `GMAIL_SENDER` — адрес того ящика, которым выдано согласие. Если Google
   ответил, что refresh-токен не выдан, отзовите прежний доступ на
   <https://myaccount.google.com/permissions> и повторите: повторное согласие
   без отзыва токен не возвращает.

**Сразу после получения токена нажмите «Publish app»** на экране согласия. Пока
приложение в статусе «Testing», Google обнуляет refresh-токен через семь дней —
и письма молча перестанут уходить, а в логе появится «Gmail не выдал токен
отправки». В статусе «In production» токен живёт, пока его не отозвать.

Публикация без верификации Google означает экран-предупреждение «Google hasn't
verified this app» при выдаче согласия (кнопка «Advanced» → «Go to … (unsafe)»)
и лимит в 100 выдавших согласие аккаунтов. Для одного ящика-отправителя это ни
на что не влияет. Для Workspace достаточно типа «Internal».

## 3. LAN-сервер

Сервер отдаёт приложение по адресу вида `http://192.168.x.x:3001` — в Google
Cloud Console для писем добавлять его не нужно (см. шаг 4 выше). Нужно ровно два
действия:

1. Положить `.dev.vars` в корень проекта на сервере — те же строки `GMAIL_*`,
   что и локально. Файл переживает `git pull`, `npm ci` и сборку.
2. Дописать туда адрес, по которому участники открывают приложение, **вместе с
   портом**:

   ```
   APP_URL=http://192.168.56.70:3001
   ```

   Порт обязателен: `start-lan.sh` поднимает воркер на 3001, и без порта ссылка
   уехала бы на 80-й, где ничего не слушает. Проверить, что именно отвечает,
   можно так:

   ```sh
   curl -s -o /dev/null -w '%{http_code}
' http://192.168.56.70:3001/
   ```

   Ссылки в письмах строятся из адреса, который видит сам воркер: за прокси он
   может видеть `localhost:3001`, и письмо уведёт в никуда. `APP_URL` закрепляет
   адрес независимо от того, что видит воркер — с ним ссылка получается
   `http://192.168.56.70:3001/api/auth/verify?token=…`.

После правки файла перезапустите сервис: `systemctl --user restart retro3d.service`.

Вход через Google на таком адресе включить нельзя: Google не принимает `http` и
частные IP как адрес возврата. Регистрация по почте, подтверждение адреса и
сброс пароля работают полностью.

## 4. Альтернатива: Resend

Если Gmail не подходит, задайте `RESEND_API_KEY` и `MAIL_FROM` — письма пойдут
через [Resend](https://resend.com) с подтверждённого там домена. Gmail имеет
приоритет: если заданы оба, используется Gmail.

## 5. Проверка

```sh
npm run dev
```

- `GET /api/auth/me` отвечает `{"google":true,"mail":true}`, когда настроено оба;
- в диалоге входа появляется «Продолжить с Google»;
- при регистрации приходит письмо; если почта не настроена, ссылка видна прямо
  в диалоге (только на localhost) и в консоли воркера.

HTTP-проверка входа при запущенном сервере:

```sh
npm run test:integration
```

Она создаёт аккаунты на адресах вида `qa-…@jinaly.test`. На такие домены письма
не отправляются: `.test`, `.example`, `.invalid`, `.localhost` и `example.com`
зарезервированы RFC 2606/6761, почты там не существует, и каждое письмо
возвращалось бы отлётом в ящик отправителя. В логе воркера видно
«домен зарезервирован под тесты» — это норма, а не сбой.

Разбор ответа Google — адрес согласия, обмен кода, проверка `id_token` — покрыт
юнит-тестами и проверяется без обращения к Google:

```sh
npm test
```

## 6. Если вход через Google не срабатывает

| Что видно | Причина |
| --- | --- |
| `redirect_uri_mismatch` на странице Google | Адрес возврата не совпадает со строкой в Console — вплоть до схемы, порта и пути. Проверьте, какой адрес видит сервер: за прокси задайте `APP_URL` или `GOOGLE_REDIRECT_URI`. |
| «Вход через Google не настроен» | Не заданы `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`: локально проверьте `.dev.vars`, на сервере — `npx wrangler secret list`. |
| «Вход через Google не завершён» | Потерялась cookie `jinaly_oauth`: между началом входа и возвратом прошло больше 10 минут либо браузер её не сохранил. |
| `invalid_client` | Секрет клиента не тот или клиент удалён в Console. |
| `Code was already redeemed` | Повторный переход по адресу возврата: код одноразовый, начните вход заново. |
| «Google не подтвердил этот адрес почты» | На эту почту уже есть регистрация по паролю, а Google не отметил адрес подтверждённым. Привязка в этом случае запрещена намеренно: иначе чужой непроверенной почтой можно было бы забрать аккаунт. |
| Письма не уходят, в консоли «Gmail не выдал токен отправки» | Refresh-токен отозван или истёк (статус «Testing» — семь дней). Получите его заново: `npm run auth:gmail-token`. |
